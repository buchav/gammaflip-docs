## How quotas work

Your account has a **daily quota** that resets at **midnight UTC**, shared by
all your API keys. API access is a **plan entitlement** (`api_access`), not a tier
name: any plan that includes it can use the API. The quota depends on the plan:

| Plan | Daily quota |
|------|-------------|
| Trial | 50 requests/day |
| Other plans with API access | 500 requests/day |

### What counts

| Endpoint | Counted? |
|----------|----------|
| `/gex/term-oi/...`, `/gex/by-strike-enhanced/...` | Yes, 1 request each |
| `/levels/...` | Yes, 1 request |
| `/history/levels/...`, `/history/timestamps/...`, `/history/snapshot/...` | Yes, 1 request each |
| `/history/files/{exchange}/{coin}` (the listing) | Yes, 1 request |
| `/history/files/{exchange}/{coin}/{date}/{file}` (a download) | No request; costs **1 file credit** (see below) |
| `/history/coverage` | **Free** |
| `/exchanges`, `/coins`, `/expirations/...` | **Free** |
| `/me` | **Free** |

Discovery and [`/me`](/api-reference/me) are free so clients and agents don't burn
quota finding out what exists or how much is left. A counted endpoint
uses one request even when it answers `400` or `404`; requests that fail
authentication or entitlement checks (`401`, `403`) are not counted.

## History file credits

Downloading a [daily history file](/api-reference/history-files) does not use your
request quota. It uses a separate daily bucket of **file credits**, so a bulk
download never eats the requests your bot needs:

| Plan | File credits/day |
|------|------------------|
| Trial | 20 |
| Other plans with API access | 200 |

The bucket resets at midnight UTC, like the request quota. One successful download
costs one credit; a `400`, `404` or `503` costs nothing. Responses to a download
carry:

```
X-History-Files-Limit: 200
X-History-Files-Remaining: 199
X-History-Files-Reset: 2026-10-07T00:00:00+00:00
```

When the credits are gone the API answers `429 history_files_limit_exceeded`
(again with no `Retry-After` header: read `X-History-Files-Reset`).
[`/me`](/api-reference/me) shows both buckets in `quota.requests` and
`quota.history_files`. For scale: 200 credits cover about 100 sessions of two
files in one day.

## Rate limit headers

Every **counted** response includes three headers (free endpoints and file
downloads don't; downloads carry the `X-History-Files-*` headers above):

```
X-RateLimit-Limit: 500
X-RateLimit-Remaining: 487
X-RateLimit-Reset: 2026-04-15T00:00:00+00:00
```

| Header | Meaning |
|--------|---------|
| `X-RateLimit-Limit` | Your daily quota |
| `X-RateLimit-Remaining` | Requests left until reset |
| `X-RateLimit-Reset` | When the counter resets (ISO 8601, UTC) |

The `rate_limit` field in the response body contains the same information:

```json
{
  "data": { "..." },
  "meta": {
    "rate_limit": {
      "limit": 500,
      "remaining": 487,
      "reset": "2026-04-15T00:00:00+00:00"
    }
  }
}
```

## Handling 429 responses

When you exceed your quota the API answers `429` and **does not send a
`Retry-After` header**. The quota resets at midnight UTC, so any honest
delay-in-seconds could be up to 86400, and HTTP clients that obey `Retry-After`
automatically would sleep for hours. Read `X-RateLimit-Reset` (ISO 8601, UTC) or
call the free [`/me`](/api-reference/me) (`quota.requests.reset`) and decide for
yourself:

```http
HTTP/1.1 429 Too Many Requests
X-RateLimit-Limit: 500
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 2026-04-15T00:00:00+00:00
Content-Type: application/json

{
  "error": "rate_limit_exceeded",
  "message": "Daily limit of 500 requests reached.",
  "rate_limit": { "limit": 500, "remaining": 0, "reset": "2026-04-15T00:00:00+00:00" }
}
```

### Recommended handling

<CodeGroup>

```python Python
import time
from datetime import datetime, timezone

def call_with_retry(fn, max_retries=3):
    for attempt in range(max_retries):
        resp = fn()
        if resp.status_code != 429:
            return resp

        reset = resp.headers.get("X-RateLimit-Reset")
        if not reset:
            time.sleep(60)
            continue

        reset_ts = datetime.fromisoformat(reset).timestamp()
        wait = max(0, reset_ts - time.time())

        # Don't wait more than an hour — surface the error instead
        if wait > 3600:
            raise RuntimeError(f"Rate limited until {reset}")

        time.sleep(wait + 1)
    raise RuntimeError("Max retries exceeded")
```

```javascript Node.js
async function callWithRetry(fn, maxRetries = 3) {
  for (let i = 0; i < maxRetries; i++) {
    const resp = await fn();
    if (resp.status !== 429) return resp;

    const reset = resp.headers.get("X-RateLimit-Reset");
    if (!reset) {
      await new Promise(r => setTimeout(r, 60_000));
      continue;
    }

    const waitMs = new Date(reset).getTime() - Date.now() + 1000;
    if (waitMs > 3_600_000) {
      throw new Error(`Rate limited until ${reset}`);
    }
    await new Promise(r => setTimeout(r, Math.max(0, waitMs)));
  }
  throw new Error("Max retries exceeded");
}
```

</CodeGroup>

## Planning your quota

The underlying GEX data updates every **15 minutes** (Lambda capture). Polling
more often than that doesn't yield new data. A typical trading bot pattern:

- `term-oi` for BTC + ETH every 15 min = 2 × 4 = **8 req/hour**
- `by-strike-enhanced` for 2-3 expirations every 15 min = ~10 req/hour
- Discovery endpoints and `/me`: **free**

**Total: ~430 req/day for a busy bot**, within the 500/day quota.

## Running out of quota?

- **Cache responses locally.** The data only changes every 15 min.
- **Use the virtual `all` exchange** (or a subset like `deribit+derive`) instead of calling each exchange separately.
- **Use [`/levels`](/api-reference/levels)** when you only need flip, regime and walls: one small call instead of a full by-strike payload.
- **Check [`/me`](/api-reference/me)** instead of probing: it is free.
- **Reduce polling frequency** to once every 30 min if you don't need sub-15-min latency.
- **Contact us** at [admin@gammaflip.io](mailto:admin@gammaflip.io) if you need a higher custom limit.
